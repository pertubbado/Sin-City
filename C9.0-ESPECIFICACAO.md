# C9.0 — Organização Inteligente de Categorias e Subcategorias

## Estado

- Etapa atual: **C9.0.1 — auditoria estrutural e congelamento da base**
- Base de produção congelada: `9c726bd6f86d08283d997b886f4f5d9be22fa383`
- Branch isolada: `feat/c9-0-organizacao-inteligente-20261101`
- Produção (`main`) não deve receber alterações antes da avaliação e aprovação explícita.

## Objetivo

Transformar a ordem estrutural das categorias e subcategorias em uma organização automática e previsível:

- categorias numeradas por posição: `01`, `02`, `03`...
- subcategorias numeradas por posição: `01.01`, `01.02`, `02.01`...
- mover uma categoria recalcula automaticamente a numeração visual dela e das categorias seguintes;
- mover uma subcategoria recalcula automaticamente sua numeração dentro da categoria;
- IDs internos permanecem independentes da numeração visual;
- códigos das regras individuais permanecem manuais e não são renumerados pela C9.0.

## C9.0.1 — Auditoria da estrutura atual

### Base confirmada

A C9.0 nasce da `main` após a conclusão da C8.0.7. O deploy #85 dessa base foi concluído com sucesso antes da abertura da branch.

### Fonte de verdade da ordem

A ordem real já é representada pelos arrays:

- `data.categories`
- `data.categories[i].subcategories`

O portal público percorre esses arrays em sequência para montar navegação, cartões da home, página da categoria e navegação anterior/próxima. Isso permite que a movimentação seja implementada por reordenação do array, sem criar um segundo campo de ordem.

### Numeração de categorias no portal

O portal público já calcula a numeração da categoria por índice (`index + 1`) em vez de depender de `category.code`. Portanto, a base pública já é compatível com numeração estrutural automática.

### Estado atual do editor

O Studio ainda:

- exibe `category.code` como campo manual;
- cria uma categoria nova com `code` calculado somente no momento da criação;
- cria novas categorias com o placeholder fixo `id: "nova-categoria"`;
- cria novas subcategorias com o placeholder fixo `id: "nova-subcategoria"`;
- não possui código persistido para subcategorias;
- não possui controles para mover categorias/subcategorias.

Isso cria risco de código visual ficar obsoleto após exclusões ou futuras movimentações e risco de IDs repetidos quando vários itens novos são criados.

### Regras individuais

`rule.code` é um campo independente e pode conter uma convenção própria da administração. A C9.0 **não deve** alterar automaticamente esses valores.

### Rotas e IDs

A navegação de categoria usa `category.id` como identidade estável. Consequentemente:

- número visual nunca deve substituir o ID;
- mover uma categoria nunca deve trocar seu ID;
- IDs existentes, válidos e únicos devem ser preservados;
- somente IDs ausentes, placeholders de criação ou duplicados devem ser reparados pela camada de normalização.

### Prévia

O editor envia `{ site, data }` diretamente para o iframe por `postMessage`. Assim, após uma reordenação, basta renderizar o Studio e enviar a prévia novamente para que a nova ordem apareça sem publicação.

### Rascunho, backup e publicação

Os três fluxos serializam `data`:

- rascunho local salva `data` no navegador;
- backup inclui `data` no JSON exportado;
- publicação gera `rulesText = JSON.stringify(data, ...)` e grava o mesmo conteúdo em `site/rules.json` e `site/content/rules.json`.

Portanto, a ordem dos arrays pode ser preservada naturalmente nesses fluxos, desde que a normalização seja executada antes da persistência quando necessário.

## Arquitetura aprovada para a C9.0

### 1. Ordem como fonte de verdade

Não criar campo `order`. A posição no array é a ordem oficial.

### 2. Numeração derivada

Helpers previstos:

- `categoryNumber(categoryIndex)` → `01`, `02`, `03`...
- `subcategoryNumber(categoryIndex, subcategoryIndex)` → `01.01`, `01.02`, `02.01`...

A numeração deve ser recalculada sempre a partir dos índices atuais.

### 3. Compatibilidade com `category.code`

`category.code` deixa de ser uma entrada manual de ordenação. Para compatibilidade com dados antigos e possíveis consumidores externos, o Studio poderá sincronizá-lo automaticamente com o número calculado da categoria antes de salvar/publicar. Ele não será usado como fonte de verdade.

### 4. Subcategoria

O código `02.03` será uma propriedade visual/calculada, não a identidade da subcategoria. Não dependeremos desse valor para rotas ou IDs.

### 5. IDs únicos e permanentes

Novos itens devem receber IDs únicos no momento da criação. A migração deve preservar IDs existentes válidos e únicos. Não renumerar IDs ao mover.

### 6. Movimentação

Primeira versão:

- botão `↑ Subir`;
- botão `↓ Descer`;
- primeiro item com `Subir` desabilitado;
- último item com `Descer` desabilitado;
- mesma regra para subcategorias dentro de cada categoria.

Arrastar e soltar fica como evolução posterior e deverá reutilizar o mesmo motor de movimentação.

### 7. UX de confirmação

Após uma movimentação, exibir confirmação clara, por exemplo:

- `✓ Categoria movida para 02 — numeração reorganizada automaticamente.`
- `✓ Subcategoria movida para 03.02 — numeração reorganizada automaticamente.`

Nenhum toast de ordenação deve publicar dados ou executar chamadas GitHub.

### 8. Acessibilidade

Controles de movimento devem possuir nomes acessíveis e estado `disabled` correto. A implementação não pode regredir os resultados da C8.0.7.

## Critérios mínimos de aceite

1. Nenhuma movimentação altera conteúdo de regras.
2. Nenhuma movimentação altera IDs estáveis existentes.
3. Numeração não pode conter lacunas ou duplicações depois de criar, mover ou excluir.
4. Subcategorias sempre herdam o número atual da categoria.
5. Códigos individuais das regras permanecem intactos.
6. Preview reflete a nova ordem imediatamente.
7. Rascunho e backup preservam a ordem.
8. Publicação continua sincronizando os dois arquivos de regras.
9. `$` / `$$`, pesquisa, navegação, temas, diagnóstico e acessibilidade da C8.0 não podem regredir.
10. Nenhum teste automatizado da C9.0 deve executar `PUBLICAR`, autenticação GitHub ou API de escrita.
